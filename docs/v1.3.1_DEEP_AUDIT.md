## Refinamento da auditoria GUI: APIs primitivas vs user-facing

A auditoria anterior reportou "39 APIs sem GUI", mas isto é grosseiro. Refinando:

### Categoria 1 — APIs primitivas (NÃO precisam GUI individual) — 5 APIs
São building blocks ou helpers internos:
- `TCCSegment` (Protocol abstrato)
- `composite_time_at_current` (helper função)
- `check_device_coordination_multi_point` (batch helper)
- `CableMaterial` (enum)
- `XfmrFaultCategory` (enum)

**Conclusão**: estas 5 APIs estão corretas em ser apenas-Python. Não precisam GUI.

### Categoria 2 — Já com GUI via dialogs v1.3.1 — 11 APIs
Acessíveis via `EquipmentEvalDialog` (Ctrl+E) ou `CoordRulesDialog`:
- EquipmentInstance, EvaluationReport, evaluate_equipment, evaluate_project, generate_html_dashboard, export_csv (G.1)
- Rule, RuleSet, RuleEngine, RuleSeverity, RuleResult (G.2)

### Categoria 3 — User-facing SEM GUI ainda — 23 APIs

**TODAS convergem em 1 fluxo**: o **TCCCoordinogramDialog populated** que estava deferred no G.3 do v1.3.1.

| Bloco | APIs | Status |
|---|---|---|
| 16 TCC Segment types (LT/ST/INST/...) | building blocks de devices | aguardam G.3 |
| 3 Device classes (TCCDevice, MultiFunctionRelay, DeviceCoordinationCheck) | container de segments | aguardam G.3 |
| 3 Damage curves (Cable, XFMR, Motor) | overlay no coordinogram | aguardam G.3 |
