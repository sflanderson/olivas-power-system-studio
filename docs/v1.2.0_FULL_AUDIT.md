### B.3 — γ: Damage curves (validação canônica detalhada)

#### γ.1 — Cable damage (NBR 5410 Tabela 43)

| Material | K (A·s^0.5/mm²) | Norma |
|---|---|---|
| Cu/PVC ≤300mm² | **115** | NBR 5410 Tabela 43, IEC 60364-4-43 Tabela A.54.2 |
| Cu/PVC >300mm² | **103** | NBR 5410 Tabela 43 |
| Cu/EPR ou XLPE | **143** | NBR 5410 Tabela 43 |
| Al/PVC | **76** | NBR 5410 Tabela 43 |
| Al/EPR ou XLPE | **94** | NBR 5410 Tabela 43 |

**Verificação**: 7 testes canônicos em `test_pp_v1_2_0_tcc_damage_gamma1.py::TestKFactorCanonical` confirmam cada valor. Nenhuma alucinação.

Fórmula: `t = (K·S)² / I²`. Validação manual:
- Cabo 50mm² Cu/PVC em 1kA: `(115·50)² / 1000² = 5750²/1e6 = 33.0625 s` ✓ (validado por test)
- Cabo 50mm² Cu/PVC em 10kA: `33.0625/100 = 0.330625 s` ✓
- Cabo 400mm² Cu/PVC em 10kA (K=103): `(103·400)²/10000² = 16.974 s` ✓

#### γ.2 — Transformer through-fault

| Categoria | K (s) | Norma | Threshold I_pu |
|---|---|---|---|
| FREQUENT | **1250** | IEEE Std 242:2001 §11.5.6 | √(1250/2) = 25 |
| INFREQUENT | **5000** | IEEE Std 242:2001 §11.5.6 | √(5000/2) = 50 |
| Mech floor | 2.0 s | IEEE C57.109 §5 | — |

Fórmula: `t = MAX(K/I_pu², 2s)`.

**HISTÓRICO ANTI-ALUCINAÇÃO**: implementação inicial usou `MIN` (incorreto). Os testes canônicos detectaram imediatamente:
- I_pu=10, K=1250: esperado 12.5s, obtido 2s (bug)
- Re-leitura cuidadosa de IEEE C57.109 §5: cap 2s é **piso inferior** em high-I, não cap superior
- Fix: `MIN → MAX`. Re-run: 18/18 verde.

Esse caso é **a evidência mais forte de que a disciplina TDD anti-alucinação funciona**: catch automático de erro em fórmula porque tests citam norma + cálculo manual.

#### γ.3 — Motor thermal

Fórmula: `t = K_motor / (I/FLA)²` onde `K_motor = locked_rotor_time_s × locked_rotor_factor²`.

| Default | Valor | Justificativa |
|---|---|---|
| locked_rotor_factor | **6.0** | NEMA Design B padrão, IEC 60079-7 |
| locked_rotor_time_s | **10.0 s** | Motor padrão Class B insulation, IEC 60079-7 §6.4.2 |
| Threshold contínuo | **1.05 × FLA** | NEMA MG-1 §12.45 (overload start) |

Validação canônica (anchor): para FLA=100A, `K = 10 × 36 = 360`. Em I=600A (LR): `t = 360/36 = 10s` ✓.

**Limitações documentadas no docstring** (não escondidas):
- Modelo single-time-constant (motores grandes precisam 2-time)
- Não distingue HOT vs COLD start
- Recomenda `TCCSegmentTimeCurrentPoints` com datasheet para precisão real

**Veredito Parte B**: todas as fórmulas e constantes têm origem normativa identificada e teste de validação. Bug detectado em γ.2 foi capturado e corrigido pelo TDD canônico.

## Parte D — Design Critique técnico (revisão de implementações α/β/γ)

### D.1 — Critique α: Segments

**Pontos fortes**:
1. ✅ Protocol `TCCSegment` runtime_checkable garante uniformidade
2. ✅ Composite via `composite_time_at_current` é função pura testável
3. ✅ Cada segment tem responsabilidade única (single segment type)
4. ✅ Edge cases tratados (M=0, M≤pickup, divisores zero)
5. ✅ `enabled` flag uniforme permite toggle sem destruir instância
6. ✅ Wrappers (OpenClearCurve/OpenClearBand) usam composição, não herança

**Pontos de atenção**:
- ⚠️ `TCCSegmentTimeCurrentPoints.point_pairs` é `tuple` (não `list`) — frozen-friendly mas perde método `append`. **Ação**: documentado, ok.
- ⚠️ `TCCSegmentAdjustableTolerance` tem `pickup_A_nominal` (vs `pickup_A` dos outros). **Ação**: justificado em docstring (3 valores conceituais), ok.
- ⚠️ `TCCSegmentAnalyticAD/SM` têm 5-8 parâmetros. **Risco** de erro do usuário ao passar valores. **Mitigação**: keyword-only seria melhor — TODO v1.2.1.

**Score técnico α**: 9/10.

### D.2 — Critique β: Devices

**Pontos fortes**:
1. ✅ `TCCDevice` frozen + tuple = imutabilidade real
2. ✅ `__post_init__` valida cada elemento isinstance TCCSegment
3. ✅ `with_segment_*` retorna nova instância (functional update pattern)
4. ✅ `triggered_segment` é diagnóstico chave para debug — **supera PTW**
5. ✅ `MultiFunctionRelay` 4 classmethods cobrem 90% dos casos práticos
6. ✅ `dataclasses.replace` preserva tipo da subclass (testado)

**Pontos de atenção**:
- ⚠️ `TCCDevice.with_segment_added` aceita qualquer TCCSegment — não valida se já tem segment com mesmo `segment_id`. **Risco baixo** (não-corrupção, só duplicação visual). TODO v1.2.1.
- ⚠️ `MultiFunctionRelay` tem keyword-only mas helpers ainda longos. **Mitigação**: documentação inline + exemplos.

**Score técnico β**: 9/10.

### D.3 — Critique γ: Damage Curves

**Pontos fortes**:
1. ✅ Cada classe cita norma explícita no docstring
2. ✅ K factors validados literais (7 testes canonical NBR)
3. ✅ Bug capturado pelo TDD canônico (γ.2 MIN→MAX) — proof-of-concept anti-alucinação
4. ✅ Limitações declaradas explicitamente (motor single-time-constant, sem XFMR inrush)
5. ✅ `__post_init__` valida inputs (FLA > 0, section > 0, etc.)

**Pontos de atenção**:
- ⚠️ NÃO segue `TCCSegment` Protocol (intencional — são curvas-limite, não funções ativas). **Mitigação**: documentado.
- ⚠️ Composição com TCCDevice no plot requer adapter (Fase δ vai resolver).
- ⚠️ Todas usam fórmula analítica I²t — não suportam datasheet tabular. **Mitigação**: documentado, recomenda `TCCSegmentTimeCurrentPoints`.

**Score técnico γ**: 8.5/10.
