## Parte E — Decisão estratégica

### E.1 — Opções

**Opção 1**: Avançar para v1.4 (Custom Label Designer arc-flash)
- **Pros**: fecha último P0 do roadmap original; deliverable visual de alto valor comercial
- **Cons**: gap GUI v1.3.0 fica acumulando — engenheiro não consegue usar Coord Rules nem Equipment Eval

**Opção 2**: v1.3.1 = GUI Integration Sweep (recomendada)
- **Pros**: fecha gap crítico; permite engenheiro USAR as 39 APIs entregues; estabelece "GUI gate" como prática
- **Cons**: adia v1.4 em ~1 semana

**Opção 3**: Híbrida — GUI integration parcial (apenas Equipment Eval Dashboard) + começar v1.4
- **Pros**: balance
- **Cons**: deixa Coord Rules pendente, complica next sprint

### E.2 — Recomendação: **Opção 2 (v1.3.1 GUI Integration Sweep)**

**Justificativa**:
1. Padrão se repete (v1.0.1 já corrigiu mesma questão) — agora com 39 APIs
2. Engenheiro final é o cliente — sem GUI, ROI é zero para ele
3. Documentar a prática "GUI gate" como invariante futuro
4. Equipment Eval Dashboard JÁ tem HTML pronto — apenas precisa abrir no QWebEngineView ou QTextBrowser
5. Coord Rules engine pode ser exposto como dialog "Verificar regras" no menu Análise

### E.3 — Escopo v1.3.1

Sub-sprints:
- **v1.3.1 G.1**: Equipment Evaluation Dashboard GUI
  - Menu Análise → "📋 Equipment Evaluation Dashboard..."
  - Dialog que coleta EquipmentInstances do projeto OU acepta dummy demo
  - Renderiza HTML do `generate_html_dashboard` num QTextBrowser
  - Botão "Exportar CSV" + "Salvar HTML"

- **v1.3.1 G.2**: Coord Rules dialog
  - Menu Análise → "🛡️ Verificar regras de coordenação..."
  - Dialog que aplica `ALL_BUILTIN_RULESETS` aos TCCDevices do projeto
  - Mostra resultados em tree/table com ícones colored

- **v1.3.1 G.3**: TCCCoordinogramDialog populated from project
  - Modificar fluxo do main_window para coletar TCCDevices + DamageCurves do .opws
  - Passar para o Coordinogram dialog (em vez de abrir vazio)

**Estimativa**: ~600 LOC + 25 testes, 1 semana de trabalho focado.
