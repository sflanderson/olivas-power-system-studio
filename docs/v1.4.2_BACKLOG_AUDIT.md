## Issues confirmadas via inspeção

### A — Logo .ico providenciado pelo user

**Evidência**: `app/resources/logo.ico` (268,286 bytes) — multi-resolução incluído.

**Problema**: `app/main.py:32-34` usa `logo.png` para `setWindowIcon`. PNG não é multi-resolução; Windows pega 1 tamanho e escala mal para 16/32px de title bar.

**Fix v1.4.2**:
```python
# app/main.py
_LOGO_PATH_ICO = _APP_RESOURCES / "logo.ico"
_LOGO_PATH_PNG = _APP_RESOURCES / "logo.png"

def _setup_application_icon(app):
    if _LOGO_PATH_ICO.is_file():
        icon = QIcon(str(_LOGO_PATH_ICO))  # multi-res
        app.setWindowIcon(icon)
    elif _LOGO_PATH_PNG.is_file():
        # Fallback PNG
        icon = QIcon(str(_LOGO_PATH_PNG))
        app.setWindowIcon(icon)
```

### C — Simbologia RELAY genérica

**Evidência**:
```
symbols.py:976: "RELAY":   RelaisSymbol,  # mesmo símbolo do Relais
```
Visualmente RELAY = Relais (chave horizontal com alavanca). Mas em PTW SLD:
- Relé de proteção = **círculo com letra "R"** dentro (como o "M" do motor) ou **retângulo com bobina + função ANSI** (50/51) escrita.

**Fix v1.4.2**: criar `RelaySymbol` em `ptw_symbols.py`:
- Círculo 30×30 com texto "R" central + indicador ANSI superior
- Pinos horizontais (linha) + pino vertical superior (TC) + pino vertical inferior (Trip)

### D — Combo Relé + Disjuntor faltante

**Evidência**: paleta atual tem RELAY (proteção) + VCB (disjuntor) separados. Em PTW, é comum ter **"Protective Device" combo** representando relé + breaker como uma unidade lógica.

**Análise técnica**: o RELAY já tem pin "Trip_out" para link com disjuntor. Mas não há atalho na paleta.

**Fix v1.4.2** (opção mais leve): adicionar componente `RELAY_BREAKER` em catalog que combina os 2 numa única caixa. Pode reusar o backend (TCCDevice + DeviceCoordinationCheck já modelam multi-function).

### G — CT Saturation vs MATLAB CT_STUDY (P0)

**MATLAB** (em `D:/000-UFMG/MVP/LIB/LIB/CT_STUDY/`):

**Nível 1 (ANSI)** — `run_level1_ansi.m`:
```
V_tap = V_capacity_full * (I_pri_nom_tap / I_pri_nom_full)
V_req = I_fault_sec * (1 + X/R) * Z_loop
I_fault_sec = I_fault_rms_A / CT_Ratio
Z_loop = R_s + R_b
PASSOU se V_tap >= V_req
```

**Nível 2 (IEC joelho)** — `run_level2_iec.m`:
```
Ek_req = I_fault_sec * (1 + X/R) * R_loop
Ek_actual = ponto onde 10%V → 50%I_e (critério IEC 10/50)
PASSOU se Ek_actual >= Ek_req
ALF necessário = Ek_req / (I_sn * R_loop)
```

**Nível 3 (Dinâmico)** — `run_level3_dynamic.m`:
```
ODE: dλ/dt = (i_st(t) - f_ie(λ)) * R_total
Curva mag estendida simétrica (positiva + negativa)
Condição inicial: λ_remanente = Kr * λ_joelho
Pior caso: phi=0 (offset DC máximo)
i_p(t) = I_peak * (sin(wt + phi - θ) - sin(phi-θ)*exp(-t/T_p))
T_p = X/R / (2π·f)
PASSOU se t_sat > t_total_ms
APROVADO COM TOLERÂNCIA se t_sat > (t_relay_ms + margin_req)
margin_req = 3.0 ms (default), 2.0 ms para IEC PR
```

**Olivas Python** (em `app/postprocessor/ct_saturation.py`):
- Tem `analyze_ansi_level1`, `analyze_iec_level2`, `analyze_dynamic_level3`, `analyze_full`
- 37 testes existentes (`test_pp_ct_saturation.py`)
- Smoke test atual no CTSaturationDialog mostra:
  - L1: V_tap=400V, V_req=440V → FALHOU
  - L2: Ek_actual=320V, Ek_req=440V → FALHOU
  - L3: t_sat=27ms, margem=+7ms → APROVADO COM TOLERANCIA

**Análise**: comportamento qualitativo bate com MATLAB. Para validação rigorosa, faria sentido criar suite de testes "MATLAB parity" com casos exatos do CT_STUDY. **Trabalho grande — defere parte para v1.4.3**.

**Fix v1.4.2 (escopo realista)**:
1. Comparar fórmulas Python vs MATLAB (linha-por-linha onde possível)
2. Aplicar correções pontuais se houver divergências
3. Adicionar 3-5 testes canonical com valores conhecidos do MATLAB
