# v1.3.1 — GUI Integration Sweep — Design Document

**Sprint**: v1.3.1 (HOTFIX GUI gap detectado em audit)
**Origem**: `docs/v1.3.0_FULL_AUDIT_GUI.md` Parte E recomendação Opção 2
**Pré-requisito**: v1.3.0 entregue (backend)
**Princípio**: documentar antes de codar; manter GUI legacy intacta.

---

## Problema

Audit pós-v1.3.0 detectou: **39 APIs novas (v1.2.0+v1.3.0), 0 referenciadas em main_window.py**. Engenheiro final não tem como acessar:
- 16 TCC segment types
- 3 multi-function device classes (TCCDevice, MultiFunctionRelay)
- 3 damage curves
- Coord Rule Engine (Rule, RuleSet, RuleEngine, 8 built-in rules)
- Equipment Evaluation Dashboard (9 critérios + HTML)

Repete o problema detectado em v1.0.1 ("Não encontrei as ferramentas adicionadas na GUI").

---

## Solução

3 sub-sprints focadas em GUI integration:

### G.1 — Equipment Evaluation Dashboard GUI

**Menu**: Análise → "📋 Avaliar Equipamentos (PTW-style)..."

**Dialog UX**:
- Botão "Adicionar equipamento" (formulário básico) OU "Carregar do projeto"
- Tabela editável com EquipmentInstances cadastradas
- Botão "Avaliar" → roda PTW_EQUIPMENT_EVALUATION em todos
- QTextBrowser exibe HTML do `generate_html_dashboard`
- Botões: "Salvar HTML...", "Exportar CSV..."

**Para v1.3.1 G.1**: começamos com **demo equipment list pré-populada** (engenheiro vê o resultado funcionando). Carregar do projeto fica para v1.3.2 (precisa parser .opws estendido).

### G.2 — Coord Rules Dialog

**Menu**: Análise → "🛡️ Verificar regras de coordenação..."

**Dialog UX**:
- Lista de RuleSets disponíveis (NEC_MOTOR, NEC_TRANSFORMER, NBR_CABLE, BEST_PRACTICES) com checkboxes
- Lista de devices/curves do projeto (ou demo)
- Botão "Aplicar regras" → engine roda
- Tree result: por device, expand para ver cada Rule + severity

**Para v1.3.1 G.2**: também começamos com demo devices.

### G.3 — TCCCoordinogramDialog populado

**Modificação**: `_on_show_tcc_coordinogram` em main_window.py.
- Atualmente: abre dialog vazio
- Novo: lê `_studies_cache` por TCCDevices/DamageCurves se presente, ou usa demo

## Plano de execução v1.3.1

### G.1 — Equipment Eval Dialog (~250 LOC + 8 testes)

1. Criar `app/gui/equipment_eval_dialog.py`
2. `EquipmentEvalDialog(QDialog)`:
   - QTextBrowser para HTML report
   - Botão "Demo": carrega 5 equipamentos hipotéticos + roda evaluation
   - Botão "Exportar CSV..." (QFileDialog.getSaveFileName)
   - Botão "Salvar HTML..."
3. Hook em main_window: menu Análise + handler `_on_show_equipment_eval`
4. Tests:
   - Dialog instantiates
   - Demo button populates QTextBrowser
   - HTML contém "PASS"/"FAIL"
   - Export CSV writes file (mock filesystem)

### G.2 — Coord Rules Dialog (~250 LOC + 8 testes)

1. Criar `app/gui/coord_rules_dialog.py`
2. `CoordRulesDialog(QDialog)`:
   - QListWidget de RuleSets (toggleable via checkbox)
   - QTreeWidget de results
   - Botão "Apply" + "Export HTML"
3. Hook em main_window: menu Análise + handler
4. Tests similares a G.1

### G.3 — TCCCoordinogramDialog modificado (~100 LOC + 5 testes)

1. Modificar `_on_show_tcc_coordinogram` para detectar projeto carregado
2. Se houver TCCDevices/DamageCurves no cache: passar para o dialog
3. Senão: demo (comportamento atual)
4. Tests: dialog aceita lista vazia, dialog aceita lista de devices

### Total v1.3.1

- ~600 LOC novo + ~21 testes
- 2 arquivos GUI novos + 3 patches em main_window
- 0 modificações em backend

## Riscos antecipados

| Risco | Mitigação |
|---|---|
| QTextBrowser não renderiza CSS inline complexo | Testar com smoke; fallback simplified HTML se necessário |
| Coord Rules dialog vira tree complicada | Limitar a 2 níveis (Device → Rules), max 50 rows |
| main_window.py vira god-class (já é grande) | Apenas adicionar 2 menu actions + 2 handlers — backend nos dialogs |
| Tests GUI lentos com QApplication | Reusar fixture `qapp` session-scoped |
