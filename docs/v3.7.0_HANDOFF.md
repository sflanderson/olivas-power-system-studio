## 3. Sprint B.2 — bus_role explicit

### Antes (v3.6.2)
`build_pf_system_from_project` fazia hardcoded "primeiro BUS = SLACK,
demais = PQ". Usuário não tinha como override; PV bus inexistente.

### Depois (v3.7.0)
NEW em `BUS.ocomp` schema:
```yaml
- name: bus_role
  label: Papel no Power Flow
  type: string
  default: "auto"
  visible: true
  group: advanced
  description: |
    auto / slack / pv / pq
    Per IEEE 399 §5 + PTW Tutorial §Part 2 p.63
```

NEW helpers em `app/gui/analysis_dialogs.py`:
* `_read_bus_role(bus)` — retorna lowercased válido ou "auto"
* `_read_bus_voltage_pu(bus)` — placeholder default 1.0 pu
* `_find_explicit_slack(bus_components)` — primeira bus com role="slack"

`build_pf_system_from_project` agora:
1. Procura bus com `bus_role: slack` → usa como SLACK
2. Caso contrário, fallback legacy (primeira BUS = SLACK)
3. Para outras buses, lê `bus_role`:
   - `pv` → `add_pv` (se sistema suporta) ou `add_pq` fallback
   - `slack` (segunda+) → defensive `add_pq` (slack único)
   - `pq` / `auto` / unknown → `add_pq`

### Backward compat
Default `bus_role: auto` mantém comportamento v3.3.1+ exato.

## 4. Sprint B.3 — q_factor com n_per_unit_per_second

### Antes (v3.6.2)
- `q_factor(t, n_per_unit_per_second=0.10)` aceita o param mas
  ignora completamente — docstring marcava "Reservado para refinamento"
- `calculate_short_circuit` no caso async motor near-gen usava
  arbitrário `ik_steady = ib * 0.5`

### Depois (v3.7.0)
`q_factor()` agora **escala** o tempo efetivo:
```python
n_ratio = n_per_unit_per_second / 0.10  # normaliza vs default
t_eff = minimum_clearing_time_s * n_ratio
# ...interpolação log-linear sobre t_eff
```

Interpretação física (IEC 60909-0:2016 §4.6.2 Tab 3):
- **n=0.10 (2-pólos)**: decaimento rápido (default backward-compat)
- **n=0.05 (4-pólos)**: decaimento mais lento (q maior)
- **n=0.02 (6-pólos+)**: decaimento ainda mais lento (q ainda maior)

`calculate_short_circuit` agora aceita
`motor_speed_gradient_pu_per_s: float = 0.10` e propaga para
`q_factor()` quando `is_synchronous_motor=False` no caso
`NEAR_TO_GENERATOR`. Cálculo: `ik_steady = ib * q`.

### Validação numérica (golden values)
- Default n=0.10, t=50ms → q ≈ 0.876
- 4-pole n=0.05, t=50ms → q > 0.876 (slower decay)
- 8-pole n=0.02, t=100ms → q ≈ 0.926

## 9. Anti-alucinação — limitações declaradas

1. **B.2 PV bus incomplete** — `add_pv` é chamado se o sistema
   suporta; senão, fallback `add_pq`. PowerFlowSystem atual pode não ter
   `add_pv` real (depende de v3.3.x). Caller deve verificar
   `hasattr(sys, "add_pv")` antes de assumir PV.

2. **B.2 múltiplos slacks declarados → defensive** — apenas o
   primeiro `bus_role: slack` é tratado como SLACK; os demais são
   convertidos para PQ defensive (matemática só aceita 1 slack).

3. **B.2 V_pu setpoint fixo em 1.0** — `_read_bus_voltage_pu`
   retorna 1.0 hardcoded. Schema BUS.ocomp não expõe `slack_voltage_pu`
   ainda; refinement deferred para v3.7.x.

4. **B.3 escala log-linear é aproximação** — IEC 60909-0:2016 Fig 8
   usa curvas tabuladas. A interpolação log-linear matches dentro de
   ~5% no range 5ms a 250ms. Para curvas exatas, deferred Weibull fit.

5. **B.3 não cobre síncronos com excitação reduzida** — q_factor
   é apenas para async motors; para síncronos com excitação reduzida
   (sub-excitação), q também varia mas com fórmula diferente
   (não implementada).
